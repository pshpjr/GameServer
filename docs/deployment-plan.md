# 개인 서버 배포·관측 구성

2026-10-21 논의 정리. 아래 내용은 구현 계획이며, 현재 배포가 완료된 상태는 아니다.

## 서버 배치
세 서버는 키 등록을 진행했으며 SSH 접속이 가능하다. 작업 기준 디렉터리 `/home/pshpjr/portfolio26` 이며 셋 모두 동일하다. 배포 설정, 이미지 전송 파일, 실행 데이터, 로그·덤프 등 프로젝트 관련 파일은 이 디렉터리 아래에서 관리한다. 세부 하위 디렉터리 구성은 구현 시 정한다.

| 서버 | 사양 | 역할 배치안 |
|---|---|---|
| 192.168.1.1 | Ubuntu 24.04, Intel N100 4코어, RAM 15GiB, SSD 512GB | 인프라 |
| 192.168.1.3 | Ubuntu 24.04, Ryzen 7 5825U 8코어 16스레드, RAM 12GiB, NVMe 512GB | 더미 클라이언트 |
| 192.168.1.5 | Ubuntu 26.04, Ryzen 5 5600X 6코어 12스레드, RAM 30GiB, NVMe 1TB 및 HDD | 게임 서버 |

각 서버들은 기존에 다른 서비스들을 제공하고 있다. 

### 작업 사항
1. systemd-coredump로 수집기 전환
   - 호스트 수집기가 덤프를 수집하고, portfolio26 컨테이너에 해당하는 덤프만 `~/portfolio26/dumps`에 추출한다.
   - 배포 시 기록한 컨테이너 ID와 수집 기록의 cgroup 정보를 대조하는 방향이며, 실제 식별 가능 여부는 시험 덤프로 검증한다. 실행 디렉터리만으로 구분하지 않는다.
   - 덤프와 함께 이미지 버전·빌드 식별 정보·수집 메타데이터를 남긴다. 원본 덤프의 보존은 호스트 수집기가 관리한다.
   - 확인 당시 1.1·1.5는 Apport, 1.3은 직접 core 파일 생성 설정이다. 수집기 전환은 호스트 전체에 적용되며 아직 수행하지 않았다.

## 이미지와 빌드

- Windows의 Docker Desktop + WSL Linux 엔진에서 `linux/amd64` 이미지를 빌드한다. 세 서버 모두 x86-64다.
- 이미지 세 개를 만든다.
  - 인프라: MySQL, OTel Collector, Prometheus, Grafana를 하나의 이미지에 포함한다. 프로세스 관리자가 각 서비스를 시작·감시·종료한다.
  - 더미: 더미 클라이언트 실행 환경.
  - 게임 서버: 게임 서버 실행 환경.
- 기존 Dockerfile과 빌드 캐시를 활용하고, 실행 전용 이미지 단계를 추가하는 방향이다.
- 성능 측정용은 `RelWithDebInfo`를 사용하고, 이미지 버전과 분석용 심볼을 대응시킨다.
- DB와 관측 데이터는 `~/portfolio26` 아래 영속 저장 공간에 두고 이미지 교체·종료 시 유지한다.

## 로컬 개발·테스트

| 환경 | 구성 | 목적 |
|---|---|---|
| 로컬 개발 | Windows에서 게임 서버·더미 직접 실행, Docker에서 인프라 실행 | 이미지 재빌드 없이 수정·디버깅 |
| 로컬 통합 테스트 | Docker Desktop에서 동일한 이미지 세 개를 사용자가 각각 직접 실행·제어 | Linux 실행·DB·통신·배포 구성 검증 |
| 서버 배포 | 역할별 이미지를 세 PC에 배치 | 부하·성능 테스트 |

- 로컬용·서버용 설정을 분리한다. 환경별 연결 주소, 포트, 데이터 경로, 실행 규모, 이미지 버전을 지정한다. 
- 로컬 통합 테스트에는 전체를 한 번에 시작·종료하는 Compose 구성을 사용하지 않는다. 인프라·게임 서버·더미의 실행·종료·재시작을 사용자가 독립적으로 제어한다.
- 로컬 설정은 이미지 재빌드 없이 교체할 수 있도록 외부 파일로 제공한다. 설정 반영에 재시작이 필요한 항목은 해당 프로세스·컨테이너만 재시작한다. 실시간 설정 반영은 별도 구현 없이는 가정하지 않는다.
- 게임 서버와 인프라를 유지한 채 더미만 종료·재실행하거나 연결을 끊는 테스트가 가능해야 한다. 더미 연결 해제를 위한 별도 조작 기능은 구현 시 정한다.
- Windows 직접 실행은 localhost의 공개 포트를 사용한다. 로컬 컨테이너 간 통신은 명시적으로 만든 공통 Docker 네트워크의 컨테이너 이름·별칭을 사용하고, 서버 간 통신은 LAN 주소를 사용한다.
- 로컬·서버 DB 데이터는 독립적으로 유지하고 초기 스키마·테스트 데이터 생성 절차를 공유한다.
- 로컬 Windows 실행은 Windows 덤프 수집 기능을 사용한다. 로컬 Linux 컨테이너의 덤프 수집 방식은 Docker Desktop 환경에서 별도로 검증한다.
- 기존 엔트리포인트의 고정된 호스트 `core_pattern` 요구 조건은 환경별 수집 방식에 맞춰 변경한다.

## 배포 소스·실행 파일·심볼 정책

- 서버 배포 빌드는 루트 저장소와 모든 중첩 서브모듈이 clean인 경우에만 허용한다. 미커밋 수정·삭제, 미추적 파일, 서브모듈 커밋 불일치가 있으면 중단한다. Git에서 제외하는 빌드 산출물은 대상이 아니다.
- 로컬 개발·테스트는 dirty 빌드를 허용하고 빌드 정보에 `dirty`를 표시한다. 서버 배포용 clean 조건을 로컬 실행에 강제하지 않는다.
- 배포 기록에는 루트·모든 서브모듈 커밋 ID, 이미지 digest, 실행 파일의 ELF Build ID를 연결한다.
- 소스는 해당 커밋을 원격 Git 저장소에 보존하고 배포 태그로 식별한다. 서브모듈의 정확한 커밋도 계속 복원 가능하게 유지한다.
- 실행 파일과 심볼은 실제 배포 이미지와 같은 빌드에서 생성한 결과를 보관한다. 
- 덤프 분석 시 배포 기록에 대응하는 소스·실행 파일·심볼을 사용한다. Git 외부의 생성 코드·빌드 입력이 있다면 버전 고정 또는 별도 보존으로 복원 가능하게 한다.

## 배포와 종료

- Windows의 설정 파일에 서버 주소, 역할별 이미지 버전, 포트, 데이터 경로, 실행 설정을 지정한다.
- Windows 제어 스크립트 하나로 SSH를 통해 세 서버를 제어한다. 서버마다 Compose를 실행한다.
- 우선 이미지 파일을 SSH로 직접 전송하고 서버 Docker에 불러오는 방식으로 구현한다. 기존 GHCR 업로드 경로는 별도로 존재한다.
- 전체 시작: 이미지·설정 전송 → 인프라 준비 확인 → 게임 서버 준비 확인 → 더미 실행.
- 전체 종료: 더미 접속 중단 및 끊어짐 로그 멈춤 → 게임 서버 저장·종료 완료 확인 → 더미 종료 → 인프라 종료. 영속 데이터는 삭제하지 않는다.
- 전체 상태 확인과 역할별 배포·재시작을 지원한다. 실패한 단계와 서버를 표시하고 후속 시작은 중단한다.
- 배포된 이미지 파일은 개발 PC 내부에 버전별로 보관한다. DB 스키마 되돌리기는 별도 설계가 필요하다.

## 관측 계획

게임 서버와 더미가 OTel Collector로 메트릭을 보내고 Prometheus에 저장하여 Grafana에서 조회한다. 상세 함수·스레드 분석은 기존 Tracy를 유지하며, OTel 분산 트레이스는 첫 구현에서 제외한다.

| 대상 | 계측 계획 |
|---|---|
| 더미 응답 | 플레이어마다 요청~대응 응답 시간을 측정하고, 그룹 전체에서 패킷 타입별 히스토그램으로 집계하여 p50·p95·p99 표시. 플레이어별 백분위수의 평균을 내지 않음 |
| 더미 진행 상태 | 요청·응답·실패·타임아웃 수, 미완료 요청 수·나이, 업데이트 지각, 연결 수·접속 실패 |
| 서버 작업 큐 | 그룹별 삽입 성공~꺼낸 직후 대기 시간의 p50·p95·p99, 큐 길이. 삽입 시도~성공까지 막힌 시간은 별도 측정 |
| 필드 | 업데이트 실행 시간·시작 지각 시간의 분포, 플레이어·몬스터 수 |
| 로그인 | 접속 시도 직전~최초 필드 입장 응답 수신 시간의 p95·p99, 실패·타임아웃 수 |
| DB | 실제 DB 연결 복구 후 작업별 큐 대기·쿼리 실행·완료 콜백 대기 시간과 오류 수 |
| 자원 | 호스트·컨테이너 CPU, 메모리, 디스크, 재시작 수 |

브로드캐스트·송신 계측은 설계 후보이며 추가 확인 후 확정한다.

- 브로드캐스트: 호출당 실제 대상 플레이어 수와 대상별 전송 메시지 수를 구분한다.
- 송신 대기량: 등록 성공했지만 전송 완료되지 않은 바이트·메시지를 추적한다. OS TCP 버퍼 잔량과는 다르다.
- 송신 정체: 미완료 송신이 있으나 설정한 시간 동안 전송 완료가 진행되지 않는 상태로 정의한다. 부분 전송·완료·폐기 경로 검토가 필요하다.

## 확인된 선행 작업

- Windows Docker Desktop Linux 엔진은 확인 당시 연결되지 않았다. 빌드 전에 기동을 확인한다.
- 현재 실제 MySQL 연결·쿼리 실행과 로그인 데이터 조회 반영이 비활성화되어 있으므로 DB 연동과 초기 스키마 구성을 복구·준비해야 한다.
- 더미의 기존 지연 표시는 요청당 평균이 아닌 플레이어별 누적 지연의 평균이다. 요청별 히스토그램으로 교체한다. 현재 응답 대응은 FIFO·패킷 타입 검증 방식이며 모든 패킷이 측정 대상은 아니다.

이번 작업에서 수행한 변경은 세 서버의 작업 폴더 생성과 이 문서 작성뿐이다.
