# 경험 카드 - 알림 → 단일 소비자 실행 패턴의 CAS 구현 비교

## 한 줄 사실

"알림을 받은 스레드 중 하나만 실행권을 얻어 쌓인 일을 비우는" 패턴을 CAS 상태 비트와 플래그+mutex 방식으로 구현해 처리량과 알리는 쪽의 꼬리 지연을 비교했고, 이 마이크로벤치에서는 상태 변경 경합이 클 때 CAS 방식이 처리량과 꼬리 지연 모두에서 앞섰고(0 / 0, 16스레드: p99 627ns 대 27,940ns), 경합이 작을 때는 평균 처리량 차이가 거의 없었다.[^1]

## 상황

* `Group::RequestUpdate`(Idle/Scheduled/Running/RunningDirty 상태를 CAS로 전환)와 Session의 recv 상태 전환이 같은 형태의 패턴이다. 소스 주석에 이 둘을 구현 방식의 기준으로 적어 두었다.
* 이 패턴을 CAS로 구현한 선택이 락 기반 구현보다 나은지 수치로 확인하려 했다. 폴더명으로 보아 CAS 상태 머신 설명 문서의 근거 자료로 만든 것으로 보이나, 작성 당시 목적은 **추가 확인 필요**.
* 환경: Windows, 논리 CPU 16개, MSVC. 시간 보정값 기준 `iters/ns` 약 5.2, `cycles/ns` 약 4.69.

## 비교한 구현

생산자 스레드가 `pending++` 후 실행권을 요청하고, 실행권을 얻은 스레드가 그 자리에서 `pending`을 비운다.

* `cas`: Busy|Dirty 비트를 CAS 루프로 전환
* `casfast`: `cas` + 이미 Busy|Dirty면 load만 하고 반환 (`Group::RequestUpdate`와 같은 early return)
* `lockflag`: 같은 Busy/Dirty 플래그를 mutex로 보호, 소비는 락 밖에서 수행

### 조건: 소비와 사이

* **소비**: 실행권을 얻은 스레드가 알림 한 건을 처리하는 데 쓰는 시간(ns)이다. 실제 `Process()`를 대신하는 값이며, 쌓인 알림이 n건이면 n번 반복한다.
* **사이**: 한 스레드가 알림을 하나 보낸 뒤(실행권을 얻었다면 소비까지 마친 뒤) 다음 알림을 보내기 전에 하는 **알림과 무관한 다른 작업**의 시간(ns)이다. 실제 서버에서 워커 스레드가 이 그룹 말고 다른 세션·그룹을 처리하는 시간에 해당한다. 코드에서는 반복문 끝의 `Work(otherNs)`다.
* 소비/사이 형태로 설정을 표기한다.
* 사이가 0이면 모든 스레드가 쉬지 않고 연속으로 알려서 상태 변수 경합이 최대가 된다. 사이가 1000ns면 각 스레드가 알림 사이에 한참 다른 일을 하므로 알림이 겹치는 빈도가 줄어든다. 
0 / 0은 상태 전환 비용만 보는 최악의 경합, 200 / 1000과 1000 / 1000은 경합이 덜한 상황이다.
* 소비와 사이는 모두 `volatile` 변수를 도는 반복문으로 시간을 채운다. 반복 횟수는 시작 시 보정한 `iters/ns`로 환산했다.

모든 조합에서 유실(`lost`)과 잔여(`leftover`)는 0이었다.

## 해석

소비 작업이 없어 상태 전환 비용만 드러나는 조건에서는 `casfast`가 가장 빨랐고 `lockflag`는 `cas`의 3분의 1 이하였다. 소비 작업이 200ns 이상 붙으면 세 방식의 평균 처리량은 거의 같아졌다. 평균 비용은 동일하나, 같은 조건에서 알리는 쪽의 p99는 `cas`/`casfast`가 수십 ns인 데 비해 `lockflag`는 500ns 이상, 0/0 에서는 수만 ns까지 커졌다. 스레드를 4개에서 64개까지 늘려도 CAS 계열의 p99는 수십~수백 ns에 머물렀다(전체는 결과 파일). 락을 잡은 스레드가 선점되거나 오래 걸리면 다른 알림 스레드가 함께 대기하기 때문으로 보이나, 원인을 따로 검증하지 않은 **추정**이다.

`casfast`는 알림 구간은 가장 짧았지만, `tail.cpp`의 전체 처리 시간(ns/op)은 소비 작업이 있는 조건에서 `cas`보다 컸다(16스레드, 소비 1000ns: 2,280 vs 1,582). 이미 예약돼 있으면 바로 떠나므로 소비가 실행권을 가진 일부 스레드에 몰리는 것으로 **추정**한다. `SPREAD` 환경 변수로 스레드별 종료 시각을 보는 코드가 있으나 그 출력은 남아 있지 않아 **확인하지 못했다**.

## 해결 결과

* 상태 변경 경합이 클 때(사이 0, 8스레드 이상)에 한해, 플래그+mutex 구현보다 CAS 상태 전환이 알리는 쪽 꼬리 지연에서 유리하다는 근거를 얻었다. 경합이 작은 조건에서는 두 방식의 평균 처리량 차이가 거의 없었다.
* `Group::RequestUpdate`의 early return과 같은 `casfast`가 알림 구간은 가장 짧지만 전체 처리 시간은 늘 수 있다는 점은 미해결로 남았다.
* 이 결과를 문서나 코드 변경에 어떻게 반영했는지는 **추가 확인 필요**.

## 배운 점

상태 변경 경합이 많지 않은 상황에서는 그냥 락을 쓰는 게 좋다. 소비 작업이 200ns 이상 붙은 조건에서는 `lockflag`도 평균 처리량이 CAS 계열과 거의 같았고(16스레드: 2.08 / 2.12 / 1.83 Mops/s), p99도 수백 ns 수준이었다. CAS가 확실히 앞선 것은 사이가 0이라 모든 스레드가 쉬지 않고 한 상태 변수에 몰리는 조건뿐이다. 이 정도 이점은 상태 변경이 정말 그렇게 몰리는 지점에서만 구현 복잡도를 감수할 가치가 있다.

## 한계

* 같은 PC, 같은 조건의 **단회 측정**이다. 반복 간 편차는 확인하지 않았다.
* 소비 작업을 `volatile` 반복문 스핀으로 흉내 냈다. 실제 `Process()`나 IO 완료 처리를 측정한 것이 아니다.
* 벤치의 Busy|Dirty 비트는 실제 코드의 4상태(Idle/Scheduled/Running/RunningDirty)를 단순화한 모델이다.
