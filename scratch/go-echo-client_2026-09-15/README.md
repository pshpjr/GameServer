# Go Echo 클라이언트

**사용할 버전: [004/main.go](004/main.go)** · [Windows 실행 파일](004/artifacts/echo-client.exe) · [검증 기록](004/TEST.md)

실행 코드는 main.go 한 파일이며 외부 패키지나 go.mod가 필요 없다. main_test.go는 검증용이다.

## 실행

PowerShell에서 실행한다.

```powershell
& .\scratch\go-echo-client_2026-09-15\004\artifacts\echo-client.exe
```

인자 없이 실행하면 아래 여섯 값을 순서대로 묻는다. 엔터는 기본값을 사용한다.

| 입력 | 기본값 | 범위 / 의미 |
|---|---|---|
| ip | 127.0.0.1 | 서버 IPv4 또는 IPv6 |
| port | 6000 | 1–65535 |
| sessions | 128 | 프로세스당 1–4096 |
| reconnect | false | true/false, y/n. 연결을 주기적으로 종료한 뒤 재접속 |
| delay | 1ms | 응답 묶음을 확인한 뒤의 대기. 숫자만 입력하면 ms, 0은 대기 없음 |
| batch | 32 | 1–4096개 패킷을 모아 전송한 뒤 응답 확인 |

CLI 인자가 하나라도 있으면 질문 없이 해당 옵션과 나머지 기본값으로 실행한다.

```powershell
& .\scratch\go-echo-client_2026-09-15\004\artifacts\echo-client.exe -ip 127.0.0.1 -port 6000 -sessions 1024 -delay 0 -batch 32
& .\scratch\go-echo-client_2026-09-15\004\artifacts\echo-client.exe -sessions 512 -reconnect -reconnect-every 10s -duration 30s
```

추가 옵션: -timeout 3s(연결 및 묶음별 제한 시간), -duration 0(무제한), -reconnect-every 10s. Ctrl+C로 종료한다. 오류가 있으면 종료 코드 1, 잘못된 옵션은 2다.

재접속을 켜면 설정한 시간이 지난 뒤 현재 묶음의 응답을 끝까지 확인하고 연결을 닫는다. 1초 후 재접속하며 오류 후에도 같은 간격으로 다시 시도한다. 꺼져 있으면 오류가 난 세션은 종료하고 다른 세션은 계속 실행한다.

## 부하 구조

- 세션당 워커 고루틴 하나. 송신·수신 또는 패킷마다 별도 고루틴을 만들지 않는다.
- 메인 루프가 초기 연결을 약 1ms 간격으로 시작한다. 4096개가 모두 연결되기까지 수 초가 걸리므로 active가 목표 세션 수에 도달한 후의 수치를 비교한다.
- 워커는 묶음 작성 → 전송 → 해당 묶음의 전체 응답 수신 및 검증 → delay 순서로 동작한다.
- 한 묶음의 패킷은 전부 보낸 후 응답을 읽는다. 동시에 진행 중인 패킷의 상한은 sessions × batch이다. batch=1은 세션별 요청/응답 방식이다.
- 송수신 버퍼를 세션별로 한 번 할당해 재사용하고, 통계는 묶음 단위로 갱신한다. 패킷별 로그는 없다.
- 초기 연결 생성과 통계 출력은 메인 루프가 담당한다. 런타임·시그널 처리 및 종료 콜백 때문에 전체 고루틴 수는 세션 수보다 조금 많을 수 있다.
- 프로토콜은 little-endian uint16 길이 8 + uint64 증가값으로 총 10바이트다. TCP가 묶음을 그대로 전달한다고 가정하지 않고 전체 바이트를 조립·검증한다.

## 시간과 처리량 읽기

| 화면 | 의미 |
|---|---|
| tx / rx | 초당 로컬 소켓 쓰기를 완료한 패킷 / 내용 검증까지 성공한 패킷 |
| batch RTT avg / p95 / max | 쓰기 시작부터 묶음 전체 수신 완료까지의 시간. p95는 히스토그램 구간 상한, max는 실행 전체 최대 |
| write | 소켓 쓰기 완료까지 걸린 시간. 소켓 버퍼·OS 대기 포함 |
| echo-wait | 쓰기 완료 후 전체 응답을 받기까지 대기 |
| local | 패킷 작성과 응답 검증에 쓴 시간 |
| pause | 설정한 delay에 따라 실제 기다린 시간. 타이머·스케줄링 영향 포함 |
| client-scheduler | Go 고루틴이 실행 가능 상태에서 실제 실행되기까지의 p95 대기 |
| active / connections / errors | 현재 연결 / 누적 연결 성공 / 누적 오류 |

RTT는 패킷 하나의 순수 서버 처리 시간이 아니다. 네트워크, 서버 큐, 클라이언트 OS 및 실행 대기가 포함된 **묶음 응답 시간**이다. write나 client-scheduler가 늘면 클라이언트 측 영향도 확인한다. local에는 모든 런타임 비용이 포함되지 않는다.

시간 통계는 측정 해상도에 따라 0으로 보일 수 있고, 실행 중 통계는 세션별 원자 카운터를 순차로 읽는 근사치다. 종료 시 진행 중이던 묶음은 취소되어 sent와 validated가 다를 수 있다.

### 상한을 정한 근거

현재 PC(Ryzen 7 9800X3D, 16논리 CPU)에서 실제 NetLibTest_Echo와 loopback으로 batch=32, delay=0 조건을 측정했다.

| 세션 수 | 결과 | 클라이언트 CPU 최대 표본 | 메모리 최대 표본 |
|---|---|---:|---:|
| 512 | 오류 0 | 21.61% | 23.14MiB |
| 1024 | 오류 0 | 19.70% | 28.07MiB |
| 4096 | 오류 0 | 23.09% | 82.98MiB |

[명령 및 측정값](004/results/scale.json), [4096세션 로그](004/results/scale-4096.log). CPU는 전체 16논리 CPU 용량 대비 500ms 간격 표본이다. 4096 검사는 연결 증가 구간을 포함한 12초 실행이며 장시간 안정성 시험은 아니다.

4096은 이 조건에서 검증한 프로세스 상한이다. 모든 하드웨어·batch·네트워크에서 병목이 없다는 보장은 아니다. 더 큰 부하는 클라이언트를 추가하고, 같은 PC의 CPU·NIC까지 포화되면 다른 PC로 나눈다. 같은 PC에서 서버와 클라이언트를 함께 실행한 수치를 원격 전용 부하 장비의 수치로 간주하지 않는다.

세션 수를 늘려도 rx가 더 늘지 않으면 batch, RTT, pause, 클라이언트 스케줄러 및 서버 상태를 함께 확인한다. 연결 수 자체가 처리량을 보장하지 않는다.

## 알려진 검증 결과

- 초기 동시 연결에서는 1024개 중 일부가 connection refused로 실패했다. 초기 연결을 약 1ms 간격으로 늘리는 방식으로 4096개 연결을 검증했다.
- batch=4096, 2세션, delay=0의 실제 서버 검사에서는 원격 연결 종료가 관찰됐다. [원본 로그](001/results/large-batch.log). 같은 크기의 독립 에코 검증은 통과했지만, 실제 서버 연결 종료의 정확한 원인은 미확인이다. 최대 batch 옵션이 이 서버에서 항상 성공한다는 의미는 아니다.
- 분할 수신, 응답 오염·길이 오류·잘림, 타임아웃, 재접속, 짧은 쓰기, 0시간 통계 경계값을 검증했다.

## 소스 빌드

Go 1.23 이상에서 사용할 수 있다. 이 작업에서는 [공식 Go 배포본](https://go.dev/dl/) 1.27.1의 ZIP과 SHA-256을 확인해 로컬 빌드에 사용했다. 시스템 설치 없이 실행 파일을 사용할 수 있다.

```powershell
go build -trimpath -o .\scratch\go-echo-client_2026-09-15\004\artifacts\echo-client.exe .\scratch\go-echo-client_2026-09-15\004\main.go
go test .\scratch\go-echo-client_2026-09-15\004\main.go .\scratch\go-echo-client_2026-09-15\004\main_test.go
```
